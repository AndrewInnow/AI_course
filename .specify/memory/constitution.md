# AI Course CLI Task Tracker Constitution
<!-- Интерактивный CLI Task Tracker (Node.js + SQLite), учебный проект -->

## Core Principles

### I. Простота прежде всего (Simplicity First)
Кодовая база MUST оставаться понятной junior-разработчику: никакой преждевременной
абстракции, никакого кода «на будущее» (YAGNI). Каждая функция должна решать задачу из
PRD; если фича отсутствует в PRD (см. раздел Non-Goals) — она не реализуется без явного
изменения PRD. Читаемость важнее краткости: осмысленные имена, простые конструкции,
комментарии только там, где логика неочевидна.

### II. Интерактивность вместо флагов (Interactive-First UX)
Основной сценарий работы — интерактивное меню с навигацией стрелками (`↑`/`↓`) и выбором
по `Enter`; пользователь MUST NOT быть обязан запоминать CLI-флаги или числовые ID задач.
После любого действия (кроме «Выход») приложение возвращает пользователя в главное меню.
Все пустые состояния (нет задач, нет тегов) MUST выводить дружелюбное сообщение и
возвращать в меню, а не обрывать программу. Некорректный ввод (пустое название и т.п.)
не приводит к падению — приложение просит повторить ввод.

### III. Локальность и надёжность данных (Local-First Data Integrity)
Все данные хранятся локально в едином файле SQLite (`tasks.db` в корне проекта, добавлен
в `.gitignore`). Схема БД (таблицы `tasks`, `tags`, `task_tags`) создаётся автоматически
при первом запуске, если отсутствует. Данные MUST переживать перезапуск приложения:
создание, изменение и удаление фиксируются в БД немедленно. При выходе (пункт меню или
`Ctrl+C`) соединение с SQLite закрывается корректно, программа завершается с кодом `0`.
Модель тегов: одна задача может иметь несколько тегов (связь многие-ко-многим через
таблицу `task_tags`).

### IV. Трёхслойная архитектура (Layered Architecture)
Код разделён минимум на три модуля с однозначной ответственностью:
- `db.js` — инициализация SQLite, схема, все SQL-запросы (CRUD + теги). Единственное
  место, где допустим SQL;
- `ui.js` — отображение меню, списков и интерактивные промпты. Единственное место,
  где допустим ввод/вывод в терминал;
- `index.js` — точка входа и главный цикл навигации; связывает `ui.js` и `db.js`,
  сам не содержит ни SQL, ни промптов.
Новые модули допустимы, но только когда существующая структура перестаёт вмещать
функциональность без дублирования.

### V. Проверка по сценариям успеха (Scenario-Based Verification)
Автоматические тесты необязательны; вместо этого каждая завершённая фича MUST быть
проверена вручную по сценариям из «Метрик успеха» PRD:
1. запуск без ошибок (`node index.js` / `npm start`);
2. полный цикл CRUD + фильтрация по тегу;
3. сохранность задач и тегов после перезапуска;
4. устойчивость к некорректному вводу.
Фича считается готовой, только когда все применимые сценарии пройдены и подтверждены
пользователем. Цвета и форматирование вывода (зелёный — успех, серый — теги,
красный — предупреждения) обязательны для читаемости консоли.

## Technology Constraints
- Среда выполнения: Node.js актуальной LTS-версии (20+ / 22+).
- Интерактивный TUI: `@inquirer/prompts` (списки, ввод текста, подтверждения).
- Цвета: `chalk` либо встроенный `util.styleText` — внешняя зависимость допустима,
  но одна; не добавлять новые библиотеки без необходимости.
- БД: `better-sqlite3` (синхронный API); нативная компиляция принимается как плата
  за простоту.
- Запрещено (Non-Goals из PRD): веб-интерфейс, REST API, облачная синхронизация,
  авторизация и мультивользовательский режим, дедлайны/уведомления/таймеры,
  приоритеты и подзадачи, экспорт/импорт в сторонние форматы.
- Документация и тексты интерфейса — на русском языке; код и идентификаторы —
  на английском.

## Development Workflow & Quality Gates
- Источник требований — PRD (`tasks/prd-cli-task-tracker.md`); расхождение реализации
  с PRD считается дефектом. Изменение требований оформляется через обновление PRD,
  а не молчаливой правкой кода.
- Работа ведётся по процессу Spec Kit: `/speckit-specify` → `/speckit-plan` →
  `/speckit-tasks` → `/speckit-implement`; конституция проверяется на этапе plan.
- Качественные ворота перед завершением фичи: код проходит сценарии принципа V,
  не содержит мёртвого кода и TODO без задачи, архитектурные границы (принцип IV)
  не нарушены.
- Промежуточные проверки: небольшие шаги реализации с подтверждением пользователя
  после каждого смыслового этапа (соответствует подходу ai-dev-tasks).

## Governance
- Настоящая конституция имеет высший приоритет над любыми другими практиками,
  стилями и предпочтениями в проекте; конфликт разрешается в пользу конституции.
- Поправки вносятся через явное обновление этого файла с указанием новой версии
  и даты; сопутствующее обоснование фиксируется в Sync Impact Report.
- Версионирование конституции: MAJOR — удаление или переопределение принципа;
  MINOR — добавление нового принципа/раздела или существенное расширение;
  PATCH — уточнения формулировок.
- Все планы и задачи (`/speckit-plan`, `/speckit-tasks`) MUST проверяться на
  соответствие конституции; несоответствие блокирует реализацию до устранения.
- Сложность (новые зависимости, дополнительные модули, отклонения от принципов)
  MUST быть явно обоснована в плане.
