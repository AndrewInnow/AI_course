# Quickstart: Приоритеты задач (Post-MVP v2)

**Feature**: 002-task-priorities | **Date**: 2026-11-25

Ручная проверка фичи по принципу V конституции. Покрывает FR-101…FR-108 и SC-101…SC-105.
Перед сценариями фичи обязательно пройти регрессию MVP (раздел «Регрессия»).

## Предварительные требования

1. Node.js LTS (20+), зависимости установлены (`npm install`).
2. Есть `tasks.db`, созданный версией MVP (с задачами и тегами). Если его нет — создайте
   его, запустив приложение из ветки 001 до применения изменений фичи.
3. Перед проверкой миграции сделайте резервную копию:
   `copy tasks.db tasks.backup.db`.

## Запуск

```bash
npm start
```

## Сценарий 1: миграция существующей базы (FR-108, SC-104, принцип III)

1. Запустить приложение на базе из MVP — ошибок на экране нет.
2. «Просмотреть все задачи»: все старые активные задачи показаны с меткой `!!` (средний),
   выполненные — без метки.
3. Статусы (`[ ]`/`[x]`) и теги старых задач совпадают с теми, что были до обновления.
4. Выйти и запустить снова — миграция не повторяется, список не меняется.

## Сценарий 2: создание с приоритетом (US1, SC-101)

1. «Добавить новую задачу» → название `Сдать отчёт`, тег `work`, на шаге приоритета выбрать
   «Высокий» → в списке `[ ] !!! Сдать отчёт #work`.
2. «Добавить новую задачу» → название `Почитать главу 3`, тег `study`, на шаге приоритета
   нажать `Enter` без перемещения курсора → в списке `[ ] !! Почитать главу 3 #study`.
3. Шаг приоритета один: форма не требует дополнительных экранов и подтверждений.

## Сценарий 3: порядок списка (US2, FR-106, SC-102)

1. Создать задачи в таком порядке: `A` (низкий), `B` (высокий), `C` (средний), `D` (высокий).
2. Открыть список. Ожидаемый порядок: `D`, `B` (высокие, новые сверху), `C` (средний),
   `A` (низкий).
3. Отметить `B` выполненной («Переключить статус»). Ожидаемо: `B` уходит в конец списка,
   после всех активных; метка приоритета у неё не выводится.
4. Фильтр по тегу: выбрать тег с задачами разного приоритета — порядок тот же правилам.

## Сценарий 4: изменение приоритета (US3, FR-107, SC-103)

1. Выбрать задачу `A` (низкий) → «Изменить приоритет» → «Высокий».
2. Ожидаемо: `✓ Приоритет обновлён`, задача `A` стоит в группе высоких (порядок по «новые
   сверху» внутри группы).
3. Выйти из приложения и запустить снова — приоритет `A` сохранён (SC-103).

## Сценарий 5: отмена и выполненные задачи (US3-2, US3-3)

1. Выбрать задачу → «Изменить приоритет» → «← Назад» — приоритет не изменился, сообщений
   об изменении нет.
2. Выбрать выполненную задачу → «Изменить приоритет» → «Низкий» — сохранено; задача
   остаётся внизу списка среди выполненных.

## Сценарий 6: пустые состояния и ввод (FR-011, SC-105)

1. На чистой базе список пуст → «Список задач пуст. Создайте первую задачу!» (без изменений).
2. Форма добавления с пустым названием → повторный запрос ввода (без изменений).
3. Шаг приоритета не занимает заметно больше времени, чем в MVP (SC-105).

## Регрессия MVP

Пройти полностью [quickstart.md MVP](../001-cli-task-tracker/quickstart.md), сценарии 1–4.
Единственное ожидаемое отличие: в форме добавления появился последний шаг «Приоритет»,
а в строках списка у активных задач — метка приоритета.

## Критерий завершённости

- Сценарии 1–6 пройдены полностью.
- Регрессия MVP пройдена без расхождений.
- Любое расхождение фиксируется как дефект с указанием шага и ожидаемого результата.
