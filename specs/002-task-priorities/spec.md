# Спецификация фичи: Приоритеты задач (Post-MVP v2)

**Feature Branch**: `[002-task-priorities]`

**Created**: 2026-11-25

**Status**: Draft

**Input**: User description: "Post-MVP фича из PRD раздела 10: приоритеты задач (высокий/средний/низкий), значение по умолчанию «средний», группировка активных задач по приоритету в списке, изменение приоритета в подменю действий"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Указание приоритета при создании задачи (Priority: P1)

Пользователь добавляет новую задачу и после ввода названия и тегов выбирает приоритет
из трёх вариантов (высокий / средний / низкий). По умолчанию предлагается «средний»:
пользователь может сразу подтвердить выбор, не меняя его. Задача сохраняется вместе
с приоритетом.

**Why this priority**: Приоритет имеет смысл только если его можно назначить; без этого
фича не существует.

**Independent Test**: Добавить две задачи — одну с приоритетом «высокий», одну с
умолчанием «средний» — и убедиться (через список после US2 или через данные), что
приоритеты сохранены.

**Acceptance Scenarios**:

1. **Given** пользователь в форме добавления задачи, **When** он вводит название,
   подтверждает шаг приоритета без изменений, **Then** задача сохраняется с приоритетом
   «средний».
2. **Given** пользователь в форме добавления задачи, **When** он выбирает приоритет
   «высокий» и подтверждает создание, **Then** задача сохраняется с приоритетом
   «высокий».
3. **Given** существующий сценарий добавления задачи из MVP, **When** пользователь
   пропускает/быстро проходит шаги тегов и приоритета, **Then** форма добавления не
   усложнилась: шаг приоритета — один выбор из трёх значений.

---

### User Story 2 - Отображение приоритета и порядок в списке (Priority: P1)

Пользователь открывает список всех задач и видит приоритет каждой активной задачи
(метка возле названия). Активные задачи сгруппированы по приоритету: высокие сверху,
затем средние, затем низкие; внутри группы — новые сверху. Выполненные задачи
по-прежнему находятся в конце списка.

**Why this priority**: Видимость приоритетов — то, ради чего фича существует: порядок
списка должен отражать срочность дел.

**Independent Test**: Создать задачи с разными приоритетами и датами, открыть список,
проверить группировку и метки приоритетов.

**Acceptance Scenarios**:

1. **Given** есть активные задачи с приоритетами «высокий», «средний» и «низкий»,
   **When** пользователь открывает список, **Then** активные задачи упорядочены:
   сначала высокие, затем средние, затем низкие; внутри каждой группы — новые сверху.
2. **Given** активная задача имеет приоритет «высокий», **When** пользователь смотрит
   список, **Then** возле названия задачи видна различимая метка приоритета (например,
   `!` / `!!` / `!!!` или словесная метка — точный вид фиксируется в контракте UI).
3. **Given** есть выполненные задачи с разными приоритетами, **When** пользователь
   открывает список, **Then** все выполненные находятся после активных, независимо
   от приоритета.
4. **Given** у задачи нет явно заданного приоритета (создана до внедрения фичи или
   с умолчанием), **When** пользователь открывает список, **Then** задача отображается
   в группе «средний» и не ломает порядок списка.

---

### User Story 3 - Изменение приоритета у выбранной задачи (Priority: P2)

В подменю действий над задачей пользователь выбирает «Изменить приоритет» и задаёт
новое значение из трёх вариантов. Изменение сразу отражается в списке.

**Why this priority**: Управление приоритетом замыкает жизненный цикл фичи: срочность
дела меняется со временем.

**Independent Test**: Создать задачу, изменить приоритет с «средний» на «высокий»,
убедиться, что задача переместилась в верхнюю группу списка.

**Acceptance Scenarios**:

1. **Given** выбрана активная задача с приоритетом «средний», **When** пользователь
   выбирает «Изменить приоритет» → «высокий», **Then** приоритет сохранён и задача
   отображается в верхней группе списка.
2. **Given** открыто подменю действий, **When** пользователь выбирает «Изменить
   приоритет» и затем «← Назад», **Then** приоритет не меняется.
3. **Given** выбрана выполненная задача, **When** пользователь меняет её приоритет,
   **Then** изменение сохраняется (и не влияет на порядок: выполненные остаются
   в конце списка).

---

### Edge Cases

- Что происходит с задачами, созданными до внедрения приоритетов? — им присваивается
  приоритет «средний» автоматически; список отображается без ошибок.
- Что происходит, когда все активные задачи имеют одинаковый приоритет? — внутри
  группы работает прежний порядок «новые сверху».
- Как выглядит приоритет выполненной задачи в списке? — метка приоритета не
  отвлекает: для выполненных задач отображение метки не обязательно (точное правило —
  в контракте UI).
- Что происходит при быстрых повторных изменениях приоритета? — каждое изменение
  фиксируется немедленно; последний выбор определяет итоговый приоритет после
  перезапуска.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-101**: Система MUST поддерживать ровно три уровня приоритета: высокий, средний,
  низкий.
- **FR-102**: Система MUST присваивать приоритет каждой задаче; значением по умолчанию
  при создании является «средний».
- **FR-103**: Система MUST позволять выбрать приоритет в форме добавления задачи
  (один выбор из трёх значений, умолчание «средний»).
- **FR-104**: Система MUST хранить приоритет как атрибут задачи (см. Key Entities).
- **FR-105**: Система MUST отображать приоритет активной задачи в списке задач
  различимой меткой возле названия.
- **FR-106**: Система MUST упорядочивать список всех задач так: активные задачи —
  по убыванию приоритета (высокие → средние → низкие), внутри группы — новые сверху;
  выполненные — после всех активных.
- **FR-107**: Система MUST позволять изменить приоритет выбранной задачи через подменю
  действий и немедленно сохранять изменение (правило немедленной записи из конституции
  распространяется на приоритет).
- **FR-108**: Система MUST при чтении задач без явного приоритета (созданных до фичи)
  интерпретировать их приоритет как «средний».

### Key Entities *(include if feature involves data)*

- **Задача (Task)**: к существующим атрибутам (идентификатор, название, статус, дата
  создания, теги) добавляется атрибут **приоритет** — перечисление из трёх значений
  (высокий / средний / низкий); ровно одно значение на задачу; значение по умолчанию —
  «средний».
- **Тег (Tag)**: без изменений.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-101**: 100% новых задач сохраняются с явно определённым приоритетом (включая
  умолчание «средний» при пропуске выбора).
- **SC-102**: При наличии активных задач всех трёх приоритетов список упорядочен
  «высокие → средние → низкие» в 100% ручных прогонов.
- **SC-103**: Изменение приоритета отображается в списке сразу после действия и
  сохраняется после перезапуска приложения в 100% случаев.
- **SC-104**: Задачи, созданные до фичи, отображаются в группе «средний» без ошибок
  после обновления (100% миграционных прогонов).
- **SC-105**: Добавление задачи с новым шагом приоритета занимает у опытного
  пользователя не более чем на 10 секунд дольше, чем в MVP (шаг не усложняет форму).

## Assumptions

- Приоритет — свойство задачи, а не тега; теги продолжают описывать категорию.
- Фильтрация по приоритету в v2 НЕ добавляется (YAGNI, принцип I конституции);
  может быть добавлена отдельной фичей при необходимости.
- Три уровня приоритета достаточны; шкала не настраивается пользователем.
- Точный вид метки приоритета в списке (символьная `!!!` или словесная) фиксируется
  на этапе планирования в контракте UI; требование — различимость и единообразие.
- Существующие данные MVP не требуют ручной миграции: отсутствие приоритета
  интерпретируется как «средний» (FR-108).
