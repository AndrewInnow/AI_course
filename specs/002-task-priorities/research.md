# Research: Приоритеты задач (Post-MVP v2)

**Feature**: 002-task-priorities | **Date**: 2026-11-25

Открытых вопросов (NEEDS CLARIFICATION) на входе не было: уровни, умолчание и поведение
списка зафиксированы в spec.md и PRD раздел 10. Ниже — решения по реализации.

## R1. Где и как хранить приоритет

**Decision**: колонка `tasks.priority TEXT NOT NULL DEFAULT 'medium' CHECK (priority IN ('high', 'medium', 'low'))`.

**Rationale**: FR-104 требует хранить приоритет как атрибут задачи. CHECK на уровне БД
гарантирует инвариант FR-101 («ровно три значения») независимо от того, какой код пишет
данные. Текстовые значения читаемы при ручной проверке файла БД.

**Alternatives considered**:
- Целое число 1–3 — компактнее, но менее читаемо в ручных запросах и при отладке; отклонено.
- Отдельная таблица `priorities` — избыточна для трёх фиксированных значений; нарушает
  принцип I; отклонено.
- Приоритет как тег (`#high`) — нарушает допущение spec («приоритет — свойство задачи, а не
  тега») и смешивает категории с приоритетами; отклонено.

## R2. Миграция существующей `tasks.db`

**Decision**: в `initDb` после создания таблиц проверяется `PRAGMA table_info(tasks)`.
Если колонки `priority` нет, выполняется
`ALTER TABLE tasks ADD COLUMN priority TEXT NOT NULL DEFAULT 'medium'`
(без CHECK — SQLite запрещает добавлять CHECK через ALTER TABLE ADD COLUMN).
Инвариант FR-101 для мигрированных баз обеспечивает `validatePriority()` в `db.js`.
Для новых БД колонка создаётся сразу в `CREATE TABLE` с CHECK. Операция идемпотентна.

**Rationale**: пользователи уже имеют файл `tasks.db` из MVP. SQLite при
`ADD COLUMN ... DEFAULT` заполняет существующие строки значением по умолчанию — задачи
автоматически получают «средний» (FR-108, SC-104) без отдельного скрипта и без потери
данных (принцип III). Проверка в слое `db.js` сохраняет инвариант для мигрированных баз.

**Alternatives considered**:
- Удалить и пересоздать БД — потеря данных; нарушает принцип III; отклонено.
- Отдельный скрипт миграции, который нужно запускать вручную — лишний шаг для пользователя
  и нарушение принципа II (интерактивность без ручных действий); отклонено.
- Не менять схему, хранить приоритет в отдельном файле — усложнение без выгоды; отклонено.

## R3. Порядок списка

**Decision**: сортировка выполняется в SQL одним выражением:
`ORDER BY t.is_completed ASC, CASE t.priority WHEN 'high' THEN 0 WHEN 'medium' THEN 1 ELSE 2 END ASC, t.created_at DESC, t.id DESC`.

**Rationale**: FR-106 — активные по приоритету, внутри группы новые сверху, выполненные в
конце. `is_completed` в первом ключе уже выносит выполненные вниз, поэтому приоритет
не влияет на их положение. Одна точка сортировки в `db.js` (принцип IV) и без повторной
сортировки в JS.

**Alternatives considered**:
- Сортировка в `ui.js` после выборки — логика раздваивается между слоями; отклонено.
- Хранить числовой ранг в колонке — дублирует знание о порядке; CASE в запросе прозрачнее
  для трёх значений; отклонено.

## R4. Визуальная метка приоритета

**Decision**: символы `!!!` (высокий), `!!` (средний), `!` (низкий) перед названием
активной задачи. Для выполненных задач метка не выводится. Над списком выводится легенда:
`Приоритет: !!! высокий · !! средний · ! низкий`.

**Rationale**: spec требует различимую и единообразную метку (FR-105), точный вид оставлен
на этап планирования. Символы читаемы без цвета — это нужно для монохромной деградации
(Assumptions spec и FR-013 не расширяются новыми цветами). Выполненные задачи уже
визуально «отключены» (`[x]`, зелёный), метка там добавляла бы шум (Edge Cases spec).

**Alternatives considered**:
- Словесные метки `[высокий]` — длиннее и визуально конкурируют с `[ ]`; отклонено.
- Цветовые метки (красный/жёлтый/серый) — не работают в монохромных терминалах и
  требуют расширения палитры FR-013; отклонено.
- Скрывать метку у средних (умолчание) — меньше шума, но ломает единообразие и затрудняет
  чтение списка; отклонено.

## R5. Выбор приоритета в UI

**Decision**: `select` из трёх пунктов в двух местах — шаг «Приоритет» в конце формы
добавления (курсор по умолчанию на «Средний») и пункт «Изменить приоритет» в подменю
действий над задачей.

**Rationale**: один выбор стрелками без ввода текста — соответствует принципу II и
SC-105 (шаг не усложняет форму). Использование того же `select`, что и в остальном
приложении, не добавляет новых примитивов UI.

**Alternatives considered**:
- Ввод цифры 1–3 — требует запоминания соответствия; хуже UX; отклонено.
- Отдельный экран «Приоритеты» в главном меню — расширяет главное меню сверх FR-001
  без необходимости; отклонено.

## R6. Взаимодействие приоритета со статусом и существующими сценариями

**Decision**: приоритет меняется независимо от статуса (в том числе у выполненной задачи).
Переключение статуса (`toggleTask`) и редактирование тегов/названия приоритет не меняют.

**Rationale**: US3-3 spec явно разрешает менять приоритет выполненной задачи; изменения
статуса и приоритета — независимые атрибуты (data-model.md, переходы состояний 001 не
затрагиваются).

**Alternatives considered**:
- Запретить изменение приоритета у выполненных — лишнее ограничение, противоречит US3-3;
  отклонено.
