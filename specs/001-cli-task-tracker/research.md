# Research: Интерактивный CLI Task Tracker (MVP)

**Feature**: 001-cli-task-tracker | **Date**: 2026-11-25

Все ключевые решения уже зафиксированы конституцией проекта и ответами пользователя;
этот документ закрепляет их с обоснованием и альтернативами. Открытых вопросов
(NEEDS CLARIFICATION) на входе в Phase 0 не было.

## D1. Драйвер SQLite: `better-sqlite3`

**Decision**: использовать `better-sqlite3`.

**Rationale**: синхронный, лаконичный API идеально ложится на CLI-приложение — запросы
возвращают результат напрямую, без промисов и callback-ов; очень распространённая,
стабильная библиотека с обширной документацией. Нативная компиляция через prebuilt-бинарники
в подавляющем большинстве случаев проходит незаметно для пользователя.

**Alternatives considered**:
- `node:sqlite` (`DatabaseSync`, встроен в Node 22.5+) — без нативных зависимостей,
  но привязывает проект к Node 22.5+; отклонено, чтобы поддерживать Node 20 LTS.
- `sql.js` (WASM) — без компиляции, но требует ручного сохранения файла БД на диск,
  что усложняет гарантию FR-014 (немедленная фиксация изменений); отклонено.
- Файл JSON вместо SQLite — не выдерживает связь многие-ко-многим и одновременные
  правки без риска порчи файла; отклонено (и SQLite явно предписан PRD).

## D2. Интерактивный TUI: `@inquirer/prompts`

**Decision**: использовать `@inquirer/prompts` (select, input, confirm).

**Rationale**: современный модульный вариант inquirer; API из отдельных функций промптов
соответствует принципу I (простота): `select` даёт стрелочную навигацию из коробки
(требование FR-001), `input` — текстовый ввод с валидацией (FR-002), `confirm` —
диалог `y/n` (FR-009).

**Alternatives considered**:
- `prompts` — легче по размеру, но обработка ошибок пользователя (например, отмена
  промпта) требует дополнительной обвязки; отклонено ради меньшего количества кода.
- Собственная реализация readline — нулевые зависимости, но стрелочная навигация,
  рендер списков и обработка Ctrl+C вручную — неоправданная сложность для MVP; отклонено
  как нарушение принципа I.

## D3. Цвета: `chalk`

**Decision**: использовать `chalk` (v5, ESM/CJS совместимость через v4-совместимую
сборку — финальная версия фиксируется при установке).

**Rationale**: де-факто стандарт цветового вывода, минимальный и читаемый API;
автоматически деградирует к монохрому, если терминал не поддерживает цвета
(требование Assumptions спеки).

**Alternatives considered**:
- Встроенный `util.styleText` (Node 20.12+/21.7+) — ноль зависимостей; принят как
  запасной вариант, если при установке возникнут проблемы совместимости с chalk;
  принципиальной разницы для MVP нет.
- ANSI-коды вручную — нечитаемый код, нарушение принципа I; отклонено.

## D4. Расположение файла БД

**Decision**: `tasks.db` в корне проекта, добавлен в `.gitignore`.

**Rationale**: решение подтверждено пользователем при ратификации конституции;
удобно для учебного контекста (курс) — база видна рядом с кодом, легко удалить
и пересоздать, не засоряет домашнюю директорию.

**Alternatives considered**:
- `~/.task-tracker/tasks.db` — удобно для глобальной установки (`npm install -g`),
  но для учебного проекта лишний шаг; отклонено (может быть пересмотрено в будущих
  версиях без изменения кода — путь вынесен в одну константу `db.js`).

## D5. Ввод нескольких тегов при создании задачи

**Decision**: комбинированный ввод — в форме добавления/редактирования задачи
пользователь выбирает существующие теги поштучно через `select` (мультиселект)
и/или добавляет новые, вводя их через запятую в одном текстовом поле.

**Rationale**: закрывает оба сценария из acceptance-сценариев US1 (выбор существующего
тега из списка и ввод нескольких тегов через запятую) без отдельного экрана управления
тегами; пустой ввод означает «без тегов».

**Alternatives considered**:
- Только свободный ввод через запятую — проще, но теряется «выбор существующего тега
  из списка» (требование PRD); отклонено.
- Один тег на задачу — противоречит решению конституции (многие-ко-многим); отклонено.

## D6. Схема данных и связи

**Decision**: три таблицы — `tasks`, `tags`, `task_tags` (см. data-model.md); связь
задача–тег многие-ко-многим; теги уникальны по имени; внешний ключ с каскадным удалением
записей связей при удалении задачи.

**Rationale**: прямо следует из FR-004 и решения конституции о модели тегов; каскад
упрощает удаление задачи (FR-009) и автоматически решает граничный случай «тег больше
не используется» — тег исчезает из списка фильтрации, когда не на что ссылаться.

**Alternatives considered**:
- Хранение тегов строкой в поле задачи (denormalized) — проще на старте, но ломает
  фильтрацию по точному тегу и дедупликацию; отклонено.

## D7. Обработка Ctrl+C и завершения

**Decision**: единая функция завершения: закрыть соединение с БД и выйти с кодом 0.
Регистрируется обработчик `SIGINT` (Ctrl+C) и точка «Выход» в главном меню.

**Rationale**: требование FR-012 и US5-сценарий 3; `better-sqlite3` закрывает соединение
синхронно, что исключает потерю уже зафиксированных данных. Транзакции на каждую
операцию записи гарантируют целостность даже при аварийном прерывании.

**Alternatives considered**:
- Полагаться на автоматическое закрытие при выходе процесса — работает, но не даёт
  гарантии кода выхода 0 и корректного вида терминала после Ctrl+C; отклонено.

## D8. Отображение длинного списка

**Decision**: в MVP — вывод списка целиком с нумерацией позиций; стрелочный выбор
задачи выполняется через `select` @inquirer (который сам обеспечивает прокрутку
при длинном списке). Пагинация не реализуется (Non-Goals дух PRD — простота).

**Rationale**: @inquirer `select` уже включает прокрутку длинных списков — отдельная
пагинация стала бы кодом «на будущее» (нарушение YAGNI).

**Alternatives considered**:
- Собственная пагинация страниц — сложность без необходимости в MVP; отклонено.

## Вывод

Все решения определены; NEEDS CLARIFICATION отсутствуют. План переходит к Phase 1
(design & contracts) без блокеров.
