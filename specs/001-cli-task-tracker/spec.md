## Clarifications

### Session 2026-11-25

- Q: Куда возвращает приложение после выполнения действия над выбранной задачей
  (переключение статуса, редактирование, удаление)? → A: В обновлённый список задач;
  в главное меню — по пункту «Назад».
- Q: Что показывать в отфильтрованном по тегу списке, когда у тега остались только
  выполненные задачи? → A: Все задачи с этим тегом независимо от статуса.
- Q: В каком порядке сортировать задачи в списке «Просмотреть все задачи»?
  → A: Активные первыми, внутри группы — новые сверху.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Добавление задачи (Priority: P1)

Пользователь запускает приложение и выбирает в главном меню пункт «Добавить новую задачу».
Приложение последовательно запрашивает название задачи (обязательное поле) и теги
(необязательное поле: можно выбрать существующие теги из списка и/или ввести новые).
После подтверждения задача сохраняется и появляется в общем списке.

**Why this priority**: Без возможности создать задачу трекер бесполезен; это первый и
основной сценарий ценности.

**Independent Test**: Запустить приложение, добавить одну задачу с тегом, убедиться, что
она появляется в списке. Полностью проверяется одним проходом меню.

**Acceptance Scenarios**:

1. **Given** приложение запущено и список задач пуст, **When** пользователь выбирает
   «Добавить новую задачу», вводит название «Купить продукты» и тег `personal`, **Then**
   задача сохраняется, пользователь возвращается в главное меню, а задача отображается
   в списке как активная с тегом `#personal`.
2. **Given** пользователь находится в форме добавления задачи, **When** он подтверждает
   пустое название, **Then** приложение не сохраняет задачу, выводит понятное сообщение
   об ошибке и просит повторить ввод.
3. **Given** в системе уже есть тег `study`, **When** пользователь добавляет новую задачу,
   **Then** он может выбрать тег `study` из списка существующих или ввести новый тег
   с клавиатуры.
4. **Given** пользователь добавляет задачу, **When** он вводит несколько тегов через
   запятую (например, `work, urgent`), **Then** все перечисленные теги связываются
   с задачей.

---

### User Story 2 - Просмотр всех задач (Priority: P1)

Пользователь выбирает в главном меню «Просмотреть все задачи» и видит полный список
задач: каждая строка содержит визуальный индикатор статуса (`[ ]` — активная,
`[x]` — выполненная), название задачи и её теги. Пустой список сопровождается
дружелюбным сообщением.

**Why this priority**: Просмотр — второй обязательный элемент цикла «добавил → увидел»;
без него добавление не подтверждается для пользователя.

**Independent Test**: Добавить 2–3 задачи (в том числе выполненную), открыть список,
проверить отображение статусов и тегов. Не зависит от фильтрации и редактирования.

**Acceptance Scenarios**:

1. **Given** в системе есть активная задача с тегами и выполненная задача, **When**
   пользователь открывает список всех задач, **Then** активная отображается как
   `[ ] Название #тег1 #тег2`, выполненная — как `[x] Название`, выполненная
   визуально отличается зелёным цветом (FR-013).
2. **Given** в системе нет ни одной задачи, **When** пользователь открывает список
   задач, **Then** он видит сообщение вида «Список задач пуст. Создайте первую задачу!»
   и возвращается в главное меню.
3. **Given** список задач открыт, **When** пользователь просматривает записи, **Then**
   рядом с каждой задачей видны все её теги.

---

### User Story 3 - Фильтрация по тегу (Priority: P2)

Пользователь выбирает в главном меню «Фильтровать задачи по тегу», видит список всех
существующих тегов, выбирает один стрелками и получает только задачи с этим тегом.

**Why this priority**: Категоризация — заявленная ценность PRD, но она опирается на уже
работающие создание и просмотр.

**Independent Test**: Добавить задачи с разными тегами, отфильтровать по одному из них,
убедиться, что показаны только задачи с выбранным тегом.

**Acceptance Scenarios**:

1. **Given** есть задачи с тегами `work` и `study`, **When** пользователь фильтрует
   по тегу `work`, **Then** отображаются только задачи с тегом `work`, остальные
   скрыты.
2. **Given** в системе нет ни одного тега, **When** пользователь выбирает фильтрацию
   по тегу, **Then** он видит понятное сообщение (например, «Теги пока не созданы»)
   и возвращается в главное меню.
3. **Given** выбран тег, у которого нет активных задач (все выполнены), **When**
   пользователь открывает фильтр, **Then** он видит все задачи с этим тегом независимо
   от статуса (выполненные — `[x]`), и может вернуться в главное меню
   (см. Clarifications).

---

### User Story 4 - Управление выбранной задачей (Priority: P2)

Находясь в списке задач, пользователь выбирает задачу стрелками и попадает в подменю
действий: переключить статус (Выполнено/Не выполнено), отредактировать название или
теги, удалить задачу (с подтверждением `y/n`), вернуться назад.

**Why this priority**: Замыкает полный цикл управления (CRUD) — без него задачи нельзя
завершить или убрать.

**Independent Test**: Создать задачу, переключить её статус, переименовать, удалить;
каждое действие проверяется просмотром списка.

**Acceptance Scenarios**:

1. **Given** выбрана активная задача, **When** пользователь выбирает «Переключить
   статус», **Then** задача становится выполненной и в списке отображается как `[x]`;
   повторное переключение возвращает статус «активна».
2. **Given** выбрана задача, **When** пользователь выбирает «Редактировать» и вводит
   новое название (или меняет набор тегов), **Then** изменения сохраняются и видны
   в списке.
3. **Given** выбрана задача, **When** пользователь выбирает «Удалить» и подтверждает
   действие (`y`), **Then** задача удаляется из списка навсегда.
4. **Given** выбрана задача, **When** пользователь выбирает «Удалить» и отвечает `n`,
   **Then** задача остаётся в списке без изменений.
5. **Given** открыто подменю действий над задачей, **When** пользователь выбирает
   «Назад», **Then** он возвращается в список задач, не изменив ничего.

---

### User Story 5 - Сохранность данных между запусками (Priority: P1)

Все созданные задачи и теги автоматически сохраняются в локальное хранилище на диске.
После закрытия приложения (пункт «Выход» или `Ctrl+C`) и повторного запуска пользователь
видит те же задачи с теми же статусами и тегами.

**Why this priority**: Пользователь ожидает, что его список дел не исчезнет; без
персистентности продукт не выполняет свою основную роль.

**Independent Test**: Добавить несколько задач, выйти из приложения, запустить снова и
убедиться, что список, статусы и теги идентичны.

**Acceptance Scenarios**:

1. **Given** пользователь создал задачи и закрыл приложение через пункт «Выход»,
   **When** он запускает приложение повторно, **Then** все задачи, статусы и теги
   на месте.
2. **Given** приложение запускается впервые (хранилища ещё нет), **When** программа
   стартует, **Then** хранилище создаётся автоматически с нужной структурой, приложение
   работает с пустым списком без ошибок.
3. **Given** пользователь прерывает работу нажатием `Ctrl+C`, **When** приложение
   завершается, **Then** оно закрывается корректно без потери введённых ранее данных
   и без сообщений об аварийном сбое.

---

### Edge Cases

- Что происходит, когда название задачи состоит только из пробелов? — приравнивается
  к пустому вводу: повторный запрос ввода.
- Как система обрабатывает тег из одних пробелов или дубликат тега? — пустой тег
  отбрасывается; повторный тег не создаёт вторую копию, а связывается с задачей один раз.
- Что происходит при очень длинном названии задачи? — название сохраняется целиком;
  отображение в списке не должно ломать структуру вывода (перенос или усечение
  при показе не теряют данные).
- Что происходит, когда пользователь пытается удалить тег у последней задачи,
  использующей его? — тег исчезает из списка фильтрации, когда ни одна задача его
  больше не использует (либо допускается хранение пустых тегов — см. Assumptions).
- Как система реагирует на `Ctrl+C` в середине ввода? — корректное завершение без
  порчи данных.
- Что происходит, когда в списке много задач (сотни)? — список прокручивается
  средствами интерактивного выбора (пагинация не реализуется, research D8);
  навигация стрелками доходит до последней записи.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST при запуске отображать интерактивное главное меню
  с навигацией стрелками `↑`/`↓` и выбором по `Enter`, содержащее пункты:
  «Просмотреть все задачи», «Фильтровать задачи по тегу», «Добавить новую задачу»,
  «Выход».
- **FR-002**: Система MUST позволять создать задачу с обязательным непустым названием;
  при пустом вводе задача не сохраняется, пользователю выводится сообщение об ошибке
  и ввод запрашивается повторно.
- **FR-003**: Система MUST позволять указать при создании задачи один или несколько
  тегов (выбор существующих из списка и/или ввод новых); теги необязательны.
- **FR-004**: Система MUST хранить для каждой задачи как минимум: уникальный
  идентификатор, название, статус (выполнена/не выполнена), дату создания и связанные
  теги.
- **FR-005**: Система MUST хранить данные локально на диске в одном хранилище,
  которое автоматически создаётся (вместе с необходимой структурой) при первом
  запуске, если отсутствует.
- **FR-006**: Система MUST отображать список всех задач с индикатором статуса
  (`[ ]` активна / `[x]` выполнена) и перечнем тегов каждой задачи; порядок — активные
  первыми, внутри группы по дате создания (новые сверху) (см. Clarifications).
- **FR-007**: Система MUST позволять отфильтровать задачи по выбранному тегу; список
  доступных тегов формируется из тегов, реально используемых задачами.
- **FR-008**: Система MUST при выборе задачи из списка показывать подменю действий:
  переключить статус, отредактировать название/теги, удалить задачу с подтверждением
  `y/n`, вернуться назад.
- **FR-009**: Система MUST запрашивать подтверждение перед удалением задачи; при
  отказе задача сохраняется без изменений.
- **FR-010**: Система MUST после выполнения любого действия (кроме «Выход») возвращать
  пользователя в главное меню (основной цикл приложения); исключением является действие
  над выбранной задачей — после него пользователь возвращается в обновлённый список
  задач, а в главное меню попадает по пункту «Назад» (см. Clarifications).
- **FR-011**: Система MUST выводить дружелюбные сообщения для пустых состояний
  (нет задач, нет тегов) и возвращать пользователя в главное меню.
- **FR-012**: Система MUST корректно завершаться при выборе «Выход» или нажатии
  `Ctrl+C`, закрывая хранилище данных, с кодом завершения `0`.
- **FR-013**: Система MUST использовать цветовое оформление для читаемости:
  зелёный — выполненные задачи и успешные операции, серый — теги, красный —
  предупреждения (например, при удалении).
- **FR-014**: Система MUST сохранять каждое изменение (создание, правка, удаление,
  смена статуса) в хранилище немедленно, чтобы данные переживали любой перезапуск.

### Key Entities *(include if feature involves data)*

- **Задача (Task)**: единица списка дел; атрибуты — уникальный идентификатор, название,
  статус (активна/выполнена), дата создания; связана с одним или несколькими тегами
  (или ни с одним).
- **Тег (Tag)**: именованная категория (например, `work`, `study`, `personal`); может
  относиться ко многим задачам; связь «задача–тег» — многие-ко-многим; уникален
  по имени.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователь запускает приложение и достигает главного меню менее чем
  за 5 секунд без каких-либо ошибок на экране.
- **SC-002**: 100% из 4 операций полного цикла управления задачами (создание, просмотр/
  фильтрация, изменение статуса и текста, удаление) выполняются корректно при ручном
  прохождении сценариев.
- **SC-003**: 100% созданных задач и их тегов присутствуют в системе после закрытия
  и повторного запуска приложения.
- **SC-004**: 100% попыток некорректного ввода (пустое название и т.п.) завершаются
  понятным сообщением и повторным запросом ввода — ни одна не приводит к аварийному
  завершению.
- **SC-005**: Новый пользователь выполняет первое добавление задачи без обращения
  к документации менее чем за 1 минуту.
- **SC-006**: Пользователь находит задачи нужной категории (фильтр по тегу) не более
  чем за 10 секунд при наличии до 50 задач.

## Assumptions

- Приложение однопользовательское и локальное: серверы, аккаунты и синхронизация
  не требуются (Non-Goals PRD).
- Данные хранятся в одном локальном файле хранилища рядом с приложением (в корне
  проекта), который исключён из контроля версий.
- Интерфейс и сообщения — на русском языке; названия задач и теги пользователь вводит
  в произвольном языке.
- Тег исчезает из списка фильтрации, когда его больше не использует ни одна задача.
- Терминал пользователя поддерживает цветной вывод и управление курсором
  (современные терминалы Windows/macOS/Linux); при отсутствии поддержки цвета
  приложение деградирует к монохромному выводу без сбоев.
- Несколько тегов вводятся комбинированно: выбор существующих из списка и/или ввод
  новых через запятую (решение зафиксировано в research.md D5).
