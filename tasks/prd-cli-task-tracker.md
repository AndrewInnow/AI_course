# PRD: Интерактивный CLI Task Tracker (Node.js + SQLite)

## 1. Введение / Обзор (Introduction / Overview)

**CLI Task Tracker** — это интерактивное консольное приложение (TUI) на Node.js для управления личными задачами с поддержкой тегов/категорий и локальным хранением данных в базе данных SQLite.

**Проблема:** При работе в терминале разработчикам и студентам неудобно постоянно переключаться в браузер или тяжелые графические приложения для ведения списка дел. Обычные консольные утилиты, требующие запоминания множества флагов и ID задач, также создают лишнее трение.

**Цель:** Создать быстрый, интуитивно понятный интерактивный терминальный интерфейс со стрелочной навигацией, который позволяет мгновенно создавать, просматривать, фильтровать по тегам и завершать задачи без выхода из консоли, сохраняя данные локально в надежной SQLite-базе.

---

## 2. Цели (Goals)

1. Обеспечить полный цикл управления задачами (CRUD) через интерактивное меню в терминале без необходимости вводить сложные CLI-аргументы.
2. Реализовать надежное локальное хранение задач и тегов в SQLite (в одном файле базы данных без установки внешних серверов БД).
3. Поддержать категоризацию задач с помощью тегов и удобную фильтрацию списка по выбранному тегу.
4. Сделать кодовую базу простой и понятной, чтобы ее мог реализовать и поддерживать junior-разработчик.

---

## 3. Пользовательские истории (User Stories)

- **Как пользователь**, я хочу запустить приложение одной командой и сразу увидеть интерактивное меню действий, чтобы не запоминать синтаксис команд.
- **Как пользователь**, я хочу создать новую задачу с названием и необязательным тегом (или списком тегов), чтобы структурировать свои дела по категориям (например, `work`, `study`, `personal`).
- **Как пользователь**, я хочу просматривать список всех задач, отфильтровать их по статусу (активные/выполненные) или по конкретному тегу, чтобы фокусироваться на нужной области.
- **Как пользователь**, я хочу выбирать задачу стрелками в списке, чтобы отметить её выполненной, отредактировать или удалить без ручного ввода числовых ID.
- **Как пользователь**, я хочу, чтобы все мои задачи сохранялись между перезапусками терминала в локальном файле базы данных.

---

## 4. Функциональные требования (Functional Requirements)

1. **Интерактивное главное меню:** Система должна при запуске отображать интерактивный список действий с навигацией стрелками (`↑`/`↓`) и выбором по `Enter`:
   - Просмотреть все задачи
   - Фильтровать задачи по тегу
   - Добавить новую задачу
   - Выйти из приложения
2. **Создание задачи:** Система должна запрашивать у пользователя:
   - Название задачи (обязательное поле, не может быть пустым).
   - Тег/категорию (необязательное поле; пользователь может выбрать существующий тег из списка или ввести новый).
3. **Хранение в SQLite:** Система должна автоматически создавать локальный файл базы данных SQLite (например, `tasks.db` в корне проекта или домашней директории пользователя) и необходимые таблицы при первом запуске, если они еще не существуют.
4. **Структура данных:**
   - Задача должна содержать как минимум: `id` (уникальный идентификатор), `title` (текст задачи), `is_completed` (булево/флаг 0 или 1), `created_at` (дата создания).
   - Теги должны быть связаны с задачами (связь «один-ко-многим» или «многие-ко-многим» через отдельную таблицу `tags` / `task_tags`).
5. **Просмотр и фильтрация задач:**
   - Система должна отображать список задач с визуальным обозначением статуса (например, `[ ]` для активных и `[x]` для выполненных) и их тегами (например, `[#study]`).
   - Система должна позволять выбрать конкретный тег из списка существующих тегов и показать только задачи с этим тегом.
6. **Действия над выбранной задачей:** При выборе задачи из списка пользователь должен получить подменю действий для этой задачи:
   - Переключить статус (Выполнено / Не выполнено).
   - Редактировать название или тег.
   - Удалить задачу (с подтверждением действия `y/n`).
   - Вернуться назад в главное меню.
7. **Обработка пустых состояний:** Если задач или тегов еще нет, система должна выводить понятное дружелюбное сообщение (например, «Список задач пуст. Создайте первую задачу!») и возвращать пользователя в главное меню.
8. **Выход из программы:** При выборе пункта «Выход» или нажатии `Ctrl+C` приложение должно корректно закрывать соединение с SQLite и завершаться с кодом `0`.

---

## 5. Не входит в скоуп (Non-Goals / Out of Scope)

- Веб-интерфейс, REST API или синхронизация с облаком/удаленным сервером.
- Авторизация пользователей и многопользовательский режим.
- Дедлайны, push-уведомления и таймеры (Pomodoro).
- Приоритеты задач и подзадачи (вложенные чек-листы).
- Экспорт/импорт в сторонние форматы (CSV, Markdown, Notion и т.д.).

---

## 6. Дизайн и UX-требования (Design Considerations)

- **Навигация:** Весь интерфейс строится вокруг последовательных интерактивных промптов. После выполнения любого действия (кроме «Выход») пользователь возвращается в главное меню (основной цикл приложения).
- **Читаемость в консоли:** Использовать цвета и четкое форматирование (например, зеленый для выполненных задач и успешных операций, серый для тегов, красный для предупреждений об удалении).
- **Очистка экрана (опционально):** Очищать консоль перед перерисовкой меню или отделять экраны четкими заголовками, чтобы не превращать терминал в бесконечную простыню текста.

---

## 7. Технические соображения (Technical Considerations)

- **Среда выполнения:** Node.js (рекомендуется актуальная LTS-версия, например Node 20+ или 22+).
- **Интерактивный TUI:** Использовать популярную и простую библиотеку для интерактивных промптов, например `@inquirer/prompts` (современный модульный вариант `inquirer`) или `prompts`. Для цветов — `chalk` или встроенный `util.styleText` в новых версиях Node.js.
- **База данных SQLite:** Рекомендуется использовать `better-sqlite3` (синхронный, очень простой API, отлично подходит для CLI без лишних callback'ов) либо встроенный в Node.js 22.5+ модуль `node:sqlite` (`DatabaseSync`), если не хочется компилировать нативные зависимости.
- **Архитектура кода:** Разделить проект минимум на 3 логических слоя для чистоты:
  - `db.js` — инициализация SQLite, создание таблиц и SQL-запросы (CRUD + работа с тегами).
  - `ui.js` — функции отображения меню и интерактивных вопросов пользователю.
  - `index.js` — точка входа и основной цикл навигации приложения.

---

## 8. Метрики успеха (Success Metrics)

- Приложение запускается без ошибок из терминала (`node index.js` или через `npm start`).
- Все 4 сценария CRUD (создание, чтение, обновление статуса/текста, удаление) и фильтрация по тегу работают корректно.
- После закрытия приложения и повторного запуска все созданные задачи и их теги сохраняются в SQLite-файле.
- При некорректном вводе (например, пустое название задачи) приложение не падает, а просит повторить ввод.

1. Может ли одна задача иметь несколько тегов одновременно, или достаточно одного тега на задачу (категория)? *(Рекомендация для быстрого MVP: один или несколько тегов через запятую, либо выбор одного основного тега).*
2. Где должен храниться файл `tasks.db` — в текущей папке проекта (удобно для разработки/курса) или в домашней директории пользователя `~/.task-tracker/tasks.db` (удобно для глобального запуска)?
